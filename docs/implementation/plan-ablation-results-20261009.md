# DeepSeek V4.1 Flash：plan 与几何后端的配对仿真实验

日期：2026-10-09。16 个预先排定的独立任务已全部结束。

## 问题与证据范围

本轮检验当前 CLI 中显式 plan 工作流、几何计算工具是否有助于定位和顺序执行。
模型使用 dsh 配置对应的 DeepSeek-V41-Flash，API 请求和返回 ID 均为 `deepseek-flash`，
`reasoning_effort=low`。实验客户端直接调用同一供应商 API，再把模型请求交给标准 MCP 和 Windows CLI；
没有启动 dsh 自带的其他代理工具。供应商只返回模型别名，因此不声称锁定了模型权重版本。

这是一轮短程仿真预实验。没有示范视频、真实相机、实机抓取或接触任务，
不用于证明 GPT-Policy 复现成功，也不能单独证明视频引导有效。

四组分别为无 plan/无几何、plan/无几何、无 plan/几何、plan/几何。
plan 是提示、task_plan 工具、持久化问题及更新流程的组合，不能解释为“是否进行内部思考”，
也不能从这轮结果单独估计持久化的效果。
无几何组仍有 RGB 图像、相机内外参和机器人反馈；模型可以自己计算坐标。
底层均采集 RGB-D，但深度数组不会作为数字矩阵直接送给模型，几何组通过 scene_query 计算它。

两个任务为“悬停红块上方”和“先蓝块后红块”，均要求指尖 TCP 位于顶面中心上方 120 mm。
每项任务用两个场景种子，每个任务×种子都运行四组；共 16 次、每组 4 次。
区组内次序预先随机排列，串行执行。初态、TCP、运动求解器、速度建议及预算一致。
每次使用独立消息历史、session UUID、CLI/profile、模拟器及任务目录。

所有组都有空任务存储容器，因为现有几何后端依赖 tasks 目录；
无 plan 组不暴露 task_plan。入口预试验曾发现这一依赖造成混杂，修正后才冻结正式协议。
预试验与正式数据分开保存，不挑选成功预试验并入正式结果。

完整协议见 [plan-ablation-protocol-20261009.md](plan-ablation-protocol-20261009.md)。

## 评分与计数口径

主评分从模型不可访问的模拟器接口取得实际 TCP 和物体坐标，
要求 XY 误差 ≤15 mm、高度误差 ≤10 mm、结束时物体相对初态位移 ≤5 mm。
顺序任务还要求动作后的采样状态先到蓝块、后到红块，最终停在红块目标。
这些是端点位置和最终物体位移判据，没有记录全程接触事件或完整路径，不能证明全程无碰撞、无接触。

位置成功、末次运动请求后成功取图、模型结束对话分别统计。
模型声称完成、控制器接受命令、运动求解器准确到达模型所猜坐标，都不代替任务评分。
运动请求计数包含被拒绝的请求；每次运动请求后都读取实际状态，不把命令目标当实际位置。

- API 次数：正式模型请求数，包含输出截断的请求。
- 工具数：通过参数验证并发送给 CLI 的模型调用，包含 CLI 返回错误的调用。
- 尝试数：还包含在客户端因参数错误或预算耗尽而拒绝的调用。
- 观察数：模型发起的 camera_observe 调用数，包含失败调用；初始观察另计。
- 每任务另有 3 次一致的准备调用：连接、初始观察、创建空存储容器。
- 图片数：新提交的图片内容块数，包含初始图；不把上下文中重复携带的图片累计为新观察。
- 用时：包含初始化、API、工具、独立评分及退出，属于本套实验装置的墙钟时间。
  工具时间包含运动后的私有评分开销，不能直接当作产品的纯执行延迟。
- token：API usage 累计值；大量前缀缓存命中，不能以总 token 直接推算费用。

每次最多 20 轮 API、40 次已发送工具调用，每轮最多 8192 输出 token。
240 秒限制的是新轮次开始；已开始的请求按各自超时结束。
正式期间未改变提示、任务、预算、阈值或运行器。分析脚本是独立只读程序。

## 实验结果

主结果：**本轮几何计算出现有利信号；当前 plan 工作流没有显示稳定收益。** 每组仅 4 次，不作显著性或通用能力结论。

| 条件 | 位置/顺序成功 | 成功且复查并结束 | 平均总时长 | 平均 API 次数 | 平均 CLI 工具数 | 平均观察数 |
|---|---:|---:|---:|---:|---:|---:|
| 无 plan、无几何 | 0/4 | 0/4 | 132.0 s | 11.00 | 12.75 | 5.00 |
| plan、无几何 | 1/4 | 1/4 | 100.5 s | 9.25 | 10.75 | 5.00 |
| 无 plan、有几何 | 3/4 | 3/4 | 89.7 s | 10.25 | 22.50 | 1.50 |
| plan、有几何 | 1/4 | 0/4 | 101.3 s | 15.75 | 26.50 | 1.25 |

表中工具数和观察数不含每任务相同的 3 次准备调用、1 次初始观察。
plan＋几何唯一位置成功的任务耗尽 20 轮 API，未完成运动后取图，故严格闭环为 0/4。
plan、无几何的较短平均时间受到两次早期截断影响，不能解释为效率提高。
成功任务平均时长：无 plan＋几何 91.4 s（3 次），plan、无几何 164.5 s（1 次）；
plan＋几何的位置成功任务 114.8 s（1 次），但未完成闭环；完全无辅助组没有成功任务。

配对比较使用完全相同的任务与场景：

- 无 plan 时增加几何：3 个区组由失败变成功，0 个反向退化，1 个双方失败。
- 有几何时增加 plan：1 个区组改善，3 个退化。
- 无几何时增加 plan：1 个改善，0 个退化，3 个双方失败。
- 有 plan 时增加几何：1 个改善、1 个退化、2 个双方失败。

这些是四个区组的描述性结果。两个任务共享两个场景种子，不把 16 次当成覆盖广泛场景的独立样本。

### 成本与行为

16 次正式任务合计 1693.6 s（28.2 分钟），185 次模型 API 请求，290 次已发送的模型工具调用，303 次工具尝试。
再加 48 次准备调用，共 338 次 CLI 工具调用；MCP 握手、list_tools 和私有评分 HTTP 请求未混入此数。
模型主动观察 51 次，加 16 次初始观察，共 67 次观察请求；新提交 86 个图片内容块。
有 34 次运动类请求，这不是 34 次实际成功运动。
没有基础设施/API 中断或自动重试；退出状态为 9 次模型结束、3 次输出截断、3 次 API 轮数耗尽、1 次工具预算耗尽。

模型 API 用时 1392.1 s，占任务总时长约 82.2%；工具及私有评分用时 221.8 s。
不能把全部 API 时间等同于三维推理时间，其中还包含网络、图像处理、计划维护与输出。
API 累计 5,066,189 total tokens，其中输出 304,011、推理 246,926；缓存命中输入很多，未估算费用。

| 条件 | 平均 API 用时 | 平均推理 token | 平均新图片块 | plan 版本冲突 |
|---|---:|---:|---:|---:|
| 无 plan、无几何 | 115.9 s | 23099 | 8.25 | 0 |
| plan、无几何 | 89.6 s | 16832 | 8.75 | 2 |
| 无 plan、有几何 | 63.1 s | 10144 | 2.50 | 0 |
| plan、有几何 | 79.4 s | 11657 | 2.00 | 16 |

无 plan 时，几何组平均总时间比无几何组少 42.3 s，同时成功更多、观察更少；
但工具调用反而更多。这与把部分坐标问题交给计算所预期的收益一致，仍不能单凭本轮拆分几何精度、模型随机性及预算的各自贡献；工具交互本身也尚不简洁。

### 阈值敏感性：事后分析，不替换主结果

无 plan、无几何的 hover_red/402 高度误差为 10.0146 mm，仅超出主阈值 0.0146 mm。
因此同时展示固定 XY=15 mm 时的高度阈值敏感性。保留原评分，不按结果挑阈值。

| 高度容差 | 无 plan 无几何 | plan 无几何 | 无 plan 有几何 | plan 有几何 |
|---|---:|---:|---:|---:|
| 5 mm | 0/4 | 1/4 | 3/4 | 1/4 |
| 10 mm（主评分） | 0/4 | 1/4 | 3/4 | 1/4 |
| 11 mm | 1/4 | 1/4 | 3/4 | 1/4 |
| 15 mm | 1/4 | 1/4 | 3/4 | 1/4 |
| 20 mm | 2/4 | 2/4 | 3/4 | 1/4 |

容差 20 mm 时无几何两组均变为 2/4，而 plan＋几何仍为 1/4。几何信号随阈值减弱，当前 plan＋几何表现较差的现象未反转。

## 具体学到了什么

1. **当前 plan 增加了可观的接口维护负担。** plan＋几何有 16 次版本冲突，plan、无几何有 2 次。
   几何写回、证据失效等会改变 plan 版本；模型批量提交旧 expected_version 或未重新读取便继续更新。
   还有 question_id 不存在、尝试写入只读 state、update 字段层级错误等。这些是当前产品可用性问题，
   不能据此宣布“规划思想无用”。正式期间没有修这些错误，也未为 plan 组补预算。
2. **表面点正确不代表选中了目标中心。** blue_then_red/401 的 plan＋几何最终红块误差合格，
   但蓝块目标偏离中心，顺序进度为 0/2。它把单个有效深度点称为 top-center，随后宣称任务完成。
   后端需要输出对象/区域的几何语义和不确定性；valid_fraction=1 只说明深度有效。
3. **“到达命令坐标”与“达到任务目标”必须分开。** 9 次模型主动结束中，5 次宣称完成却未通过独立评分，
   包括上面的 10.0146 mm 边界例。另一些报告用 supported=false 的接触传感器零值佐证无接触，证据并不成立。
   结果核验不能交给模型自我宣告，也不能只比较 FK 与自己猜测的坐标。
4. **低思考强度仍会截断。** 三次达 8192 输出 token，其中两次 reasoning_tokens=8192，另一次为 7947。
   它们是固定预算下的失败，不是连接故障；本轮未重试或放宽预算。
5. **运动可达性也混在任务难度里。** 一个无辅助任务反复遇到 IK 拒绝，之后关节动作 outcome_unknown 并锁存停止。
   事后、未反馈给模型的只读 IK 检查发现四个真实目标均有解；但 seed401 红块解的 J4 约 88°，接近 89°上限。
   这只说明目标存在数值解，不证明所有误差目标、姿态或路径都可行；不能把失败全部归因于视觉。

## 下一步建议：保持下位机固定，缩短模型需要维护的链条

优先做一个小切片：模型提供目标区域及所需关系，几何后端一次返回区域平面、中心/候选点、误差范围和证据 ID。
让模型选择“接下来缺什么证据”，避免几十次单点取样，也避免把单点深度直接称为物体中心。
服务器继续校验版本和证据新鲜度，但前端应减少模型手工维护版本的次数；不能靠删除一致性检查来消除报错。

plan 暂时缩成简短的目标、关键问题和成功判据，保留必要持久化。下一轮在几何后端固定时，
比较轻量 plan 与当前完整工作流/无显式 plan，检验是否真正减少错误和开销。不要同时换模型、控制器和全部感知组件。

视频收益需要另开受控实验：先固定一种已验证的几何与交互接口，再比较有无相关示范视频，
并可增加无关视频对照。任务需包含仅靠目标文字难以指定的动作顺序或接触方式，
例如从哪一侧插入把柄、何时夹紧和提起；本轮悬停任务不能回答这种问题。增加场景和重复次数前先确定预算。

以上是后续建议，本轮没有偷偷修改生产管线后再混入结果。
