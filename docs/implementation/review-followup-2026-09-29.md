## 实际交互简化

- 单个配置提案用 `/confirm` 或 `/cancel`；多个提案仍明确指定编号，避免误选。
- `/approval` 重复设置当前模式、`/limits` 无改动时不再要求确认。
- 限位向导拿不到当前策略时直接返回，避免生成基于空配置的修改。
- `/help` 给出连接、工具调用、向导和退出路径；说明新仿真 auto、真机 risk 与已有配置保留。

## Codex 自查与修正（第二轮）

范围是本次未提交改动、相关前端调用路径和仿真测试，不代表全仓库或真机验收。

发现并修正：

1. **P1：无操作提示留下旧提案。** 当前 risk → `/approval auto`（待确认）→ `/approval risk` → `/confirm` 原先会执行旧 auto 提案。修正为：仅在没有待确认提案时省略无改动确认；存在旧提案时保持明确选择。JSON 和向导的无改动分支同样处理，保留旧确认码接口。
2. **P1：策略读取失败后的编辑入口不一致。** 之前只阻止了向导，JSON `/limits` 和 `/approval` 仍能生成缺少原限制的提案。三个入口现在共用一个小的读取函数；失败统一返回，去掉重复读取与默认空策略的分支。
3. **P2：向导询问当前模式不用的阈值。** auto/always 原先仍需回答七项；现在只问执行限制的三项，risk 才问四个自动审批阈值。原阈值保留，不改变后端审批语义。
4. **测试证据过宽。** 默认仿真回归原先只验证“不等待审批”和“HTTP 失败”，没有排除执行失败或 busy。现在要求前一动作 succeeded，后一请求明确返回 joint_limits/422，且没有新增后端命令。

工程化判断：共享字面量检查、共用策略读取有实际重复调用支撑；没有增加包、依赖、配置层、插件注册器、策略框架或 dev/prod 分支。相对已提交基线，三个运行代码文件合计净减少 16 行（不含测试和文档）。会话、鉴权与幂等继续留在后端，不要求用户在正常流程中手动管理。

保留的使用成本：多项配置同时待确认时仍需编号；限位向导仍是逐项填写。没有在这轮为了消除这些分支重写确认系统或异步终端。后续若继续简化，应从实际操作卡点出发，不按文件数或测试数拆模块。
