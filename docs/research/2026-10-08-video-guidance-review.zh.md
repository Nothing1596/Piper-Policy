# 视频引导管线：研究与代码对照（2026-10-08）

本轮是研究审查和设计建议，不是已批准的实现方案。用户已断开真机；本轮没有连接设备或发送动作。审查的是本机 `40d231b` 加现有未提交的视频/前端改动，不代表已发布版本。没有覆盖这些改动。

**结论**

固定 PiperX 执行端、研究视频如何帮助通用模型完成任务，是合理的实验边界。但主要对照中还应固定执行模型、工具、运动参数、相机和标定，只改变上下文构造方法。否则不能把成功率变化归因于视频管线。

现有代码具备示范编译、真实图片传递、连续取帧、深度查询、确定性运动求解及记录的基础；还不是 GPT-Policy 的等价复现，也没有证明分层视觉优于直接观看。最值得优先检验的是：在有限图像预算下，保留与当前操作阶段有关的接触前后证据，并按执行进度取回它们，是否改善方法遵循和任务完成。

**参考实现真正提供了什么**

| 工作 | 已核对的方法 | 对本项目的启发与边界 |
|---|---|---|
| GPT-Policy | 历史示范与当前观察分别标记，图文交错进入模型；视频选择器按窗口选择，再全局审阅，关注接触、释放、角色和可见结果；下层执行结构化动作并反馈 | 直接基线。语义选帧和摘要已经存在，单纯再加入这两项不足以构成新贡献 |
| LongVIL | 对候选动作检查对应片段的时间一致性，再检查结束帧的空间关系，另用模型核对计划和代码 | 借鉴局部视频证据核对；模型核对不是物理真值。公开 SpatialVerify 提示要求模糊时也选最可能方向，不能照搬成真实接触判定 |
| NeSyCR | 将示范转成状态/动作的符号表示，验证前置条件与效果；在部署条件改变时模拟并修订程序 | 借鉴“方法是否适用于当前场景”的检查。字符串形式的 preconditions 不等于已有符号验证器；现阶段无需复制完整 PDDL 系统 |
| SeeDo | 手部运动选帧、对象分割/跟踪、视觉标记、VLM 动作计划和执行 | 检测器服务于对象身份和交互事件；检测整只杯子不等于定位杯柄抓取部位 |
| DITTO | 从 RGB-D 人类示范中提取物体相对运动，再匹配当前场景并变换轨迹 | 几何迁移与语义引导是不同方法。任意 RGB 视频不具备这一路线需要的度量信息 |

**当前代码对照与具体缺口**

1. `piper-lab/src/piperlab/demonstration/compiler.py` 已有候选筛选、分批看图、阶段/效果/不确定性和证据引用。校验主要确保字段、引用 ID 和时间顺序合法，不验证“该图确实支持该效果”。全局语义调用仍只直接看有限张图，其余选帧作为文本信息进入。因此不能将结构校验通过标作视觉语义验证通过。
2. `piperx-cli/src/piperx_middleware/console_interaction.py:371` 默认调用 `reference()`，后者默认 `offset=0, limit=3`。当前初始示范图片偏向开头三张，而非完整流程概览；后续依赖模型主动翻页，没有基于当前阶段自动检索的机制。
3. `video/watch.py:80` 先按请求区间均匀取帧；pipeline 虽运行全视频 CV 分析，却没有直接用该分析的事件候选替换本次观看帧。快速 VLM 在这些观看帧中再取首、尾及变化最大的中间帧，至多三张。这不保证接触或插入片段进入模型输入。
4. `demo_bridge.py:198` 将发送给执行模型的 pipeline 图片过滤为 `vision.frames_supplied`。因此快速视觉层遗漏的图片也不会在该次响应中交给执行模型；可另行 direct 回看，但需要额外调用。建议把“快模型看过哪些图”和“执行模型允许看哪些证据”分开。
5. `DemoBridge.prepare()` 未把配置中的 `detector_onnx` 传给 compile 子进程；独立 `piper-video demo compile` 所复用入口本身支持该参数。watch 使用普通 `OnnxDetector`，独立 compile 可使用 `TrackedDetector`；prepare、compile、watch 目前不是同一套感知能力，不宜统一描述为 YOLO+跟踪全接通。
6. `live_frames.py:66` 的实时策略是首末帧加灰度变化/清晰度排序，可选 ROI；不理解操作阶段，也未补偿腕部相机运动。ROI 输出在 `live_camera.py:131` 优先替代全图，容易损失空间参照。建议关键阶段给一张全图与局部裁剪，而非只给局部图。
7. `policy/runner.py:55` 明确只接受 MuJoCo；`policy/verify.py` 的独立验证限定于红蓝小块和绿色放置区域。这些能力不能算作真机 CLI 已具备通用抓取验证。真机 CLI 的 `visual_evidence` 目前主要提供素材，不能仅依据其存在就推进任务阶段。
8. 运动接口名称接近不表示语义等价。`primitives.py:66` 的 move_to/move_by/rotate 求目标 IK 后走关节端点；move_linear 单独采样路径。GPT-Policy 对其笛卡尔工具描述的是路径插值、连续种子 IK 和轨迹定时。可以保留 PiperX 的实现做本平台对照，但不能声称仅替换了同构硬件适配器。

**建议只围绕一条主线改进**

一条共享视频基础设施，两种上下文用途：示范回答“应该怎么做”，实时观察回答“当前是什么状态、上一步是否产生预期效果”。二者共享解码、缓存、图像存储和来源标记；阶段、时效、坐标含义保持独立。

示范离线整理一次，产出轻量阶段记录：时间区间、操作对象/部位、接触或相对关系、前置状态、预期可见效果、原始证据引用及不确定性。优先复用现有 stage 格式，新增字段须服务具体检索或判断。以抓杯柄为例，记录接近杯柄、手指穿过开口/包住柄、闭合、杯子随手上移等可见过程；被遮挡的接触标 unknown，不能由前后结果补造细节。

候选生成保留粗略全片覆盖，同时提议手—物距离变化、部件遮挡改变、对象相对运动等局部区间。便宜检测器提供区域，不决定动作是否成功；快速 VLM负责分段及关系描述。对关键区间回读原视频，保留接触前/过程/后证据。三帧若不够则扩展区间，而不是把固定三帧当作完整动作。手部跟踪适用于示范；执行端用夹爪状态及可见对象关系，不假设人手与夹爪外形相似。

执行时维护一个很小的阶段状态。每轮提供任务、简短全局示范概览、当前阶段及相邻阶段的证据、最新实时图像和上次动作结果。阶段选择依据当前可见关系和执行历史，不能按时间或动作次数硬推进；允许 unknown、停留和回退。提出“已夹住”时，应寻找物体随夹爪移动、柄与夹指相对位置等后果，不能仅看夹爪闭合或二维重叠。

实时选帧应围绕动作实际开始、实际完成/稳定及异常组织，保留最新图像。发生腕部大运动时，将相机运动与对象运动区分；有可信标定时使用相机姿态辅助几何解释，否则降级为未补偿的视觉证据。模型不确定时按阶段回看示范、放大部位或观察另一视角，按需求获取信息。

这条设计是待验证假设。它可能因错误阶段识别或过度压缩而不如直接多帧观看，必须保留原图回看和公平基线。

**固定执行端时还需要固定哪些条件**

不只固定机械臂型号，还要固定工具定义、SDK/执行器版本、TCP、相机安装与标定、轨迹路径语义、速度、反馈新鲜度、停止/到位判据、审批方式和决策预算。先解决“任务终态与机械臂真实到位不同步”的实验基础问题，再冻结版本；同一轮消融中不可一边修改这些条件一边归因视频收益。

普通人类 RGB 示范提供方法和约束，不能提供可靠的部署坐标。腕部 RGB-D 点换到基座需要同一时刻的机械臂位姿与外参，例如 `p_base = T_base_flange(q_t) · T_flange_camera · p_camera`。相机看到的深度也不等于指尖到杯柄的间隙；还需要指尖/TCP几何。示范更清楚不能补偿错误外参。几何能力应对所有实验条件一致开放。

**最小实验设计**

先固定执行模型及实时观察策略，仅比较历史示范上下文：

| 条件 | 输入 | 目的 |
|---|---|---|
| A | 指令和实时观察，无示范 | 测任务常识基线 |
| B | 原样或忠实移植的 GPT-Policy 示范上下文构造 | 核心参考基线，记录参数和快照 |
| C | 当前项目的 compile/watch 与分页策略 | 判断现有实现的真实水平 |
| D | 阶段对应的接触前后证据检索 | 检验拟议贡献 |

各条件使用相同任务/初始摆位分组，随机执行顺序，每次清空模型会话和上次试验提示。B/C/D控制每轮及整回合图片像素、token、模型调用和时间预算；离线整理成本单独列出，并给总成本。若D多用快模型，要增加同预算基线或移除快模型的消融，避免把额外推理预算误认成选帧方法收益。

先做约3种可复位任务、每种少量试验排查协议，再用先导结果确定正式样本量。后续把“示范处理旧/新 × 实时选帧旧/新”做2×2对照，区分两种视频处理的贡献。换执行模型用于后续泛化验证，不与第一轮主比较同时改变。

任务要让示范带来指令之外的信息。例如同样的提起/放置目标，示范指定不同可行抓取部位或不同操作顺序。若指令已把抓柄方法、方向和步骤全部写明，只能检验视频的附加收益，不能充分检验从视频获得策略。设置文字方法摘要、最终目标图、人工选择关键片段等对照，以区分程序信息、目标信息和自动选帧误差。

离线评价：独立人工标注关键交互时间段、操作部位、前后关系及遮挡，统计关键事件证据覆盖率、次序错误、阶段匹配错误、错误接触断言与检索开销。现有 `demonstration/annotations.py` 可复用；合成单测不能代替真实视频标注。

实机评价：任务成功、方法遵循、人工介入、首次正确接触、重试、假成功、决策数、总耗时和tokens。成功判断使用统一事先定义的可观测标准，由与生成管线分开的人工或测量方式评价；不能拿快速 VLM 对自身摘要的评价作真值。即使只有一个控制相机，也可以用不进入模型输入的独立录像辅助人工评价。

按任务报告分组/配对的结果和不确定区间；不要把同一段视频的数百帧算成数百个独立试验。硬件故障预先规定为失败/中断并单列，所有条件同口径，不事后删除不利回合。现有 shuffled 对照保留原时间戳，可被模型重排，不能作为强因果证据；必要时使用一致且受控的缺事件/错关系输入，先离线检验。

**建议的最小实现切片（尚未执行）**

保留现有 CAN、HTTP/MCP、CLI、编译器和记录体系。只做：

1. 修通上述 detector 参数、示范全局概览和原始证据传递；watch 重看缓存已有分析，不每次重做全片分析。
2. 在已有示范工具上增加按阶段/问题取证据，记录返回的时间范围、部位裁剪与证据缺口；先不建设通用知识图谱或符号规划框架。
3. 同一执行循环加入轻量阶段更新与动作前后观察组装，接上离线标注评价及配对实验记录。

第一份交付应是同一个抓杯柄视频在 B/C/D 下给执行模型的实际上下文对比，以及人工标注的关键事件覆盖。先确认“模型收到的信息确实改善”，再消耗真机试验时间。
