# 示范参考与实时观察的边界

## 示范视频的作用

示范给执行模型提供操作方法、动作顺序、物体角色和目标状态。它是部署时的上下文，不意味着模型参数更新，也不提供另一台机械臂可直接重放的关节轨迹。人类视频尤其缺少机器人动作标签和已标定的执行坐标。

GPT-Policy 的原论文把示范参考、当前图像/机器人状态、交互历史和上一工具结果分别组织到同一个模型输入。自动选帧保留初始/结束、接触/释放与角色变化，而不是只取运动最大的几帧。原论文小样本实验中，毛巾/笔记本任务有人类视频时均为 2/3，无视频均为 0/3；这支持相关示范的作用，不能证明所有视频都会改善执行。

来源：[原论文方法、实验与附录](https://arxiv.org/html/2609.19138v1)。

## 一个基础设施，两种处理策略

解码、检测、图像存储、来源标记与模型传输可以共用。任务角色、选帧目标、缓存和时效必须分开：

| | 示范参考 | 实时观察 |
|---|---|---|
| 主要问题 | 应该用什么方法、遵循什么顺序 | 当前在哪里、上一步实际发生了什么 |
| 时钟 | 源视频 PTS/相对时间 | 相机接收时间与机器人状态接收时间 |
| 关键帧 | 阶段边界、接触前后、释放、结束状态 | 最新画面、动作前后、夹爪变化、异常 |
| 缓存 | 任务期间保留，可反复查询 | 短时缓存，旧观察明确过期 |
| 快速视觉模型 | 可在任务前整理、摘要、评价 | 按需调用，不阻塞每帧反馈 |
| 能支持的结论 | 历史方法及可见效果 | 当前状态与当前动作的结果证据 |

本项目当前 DemoBridge 和 LiveCamera 已分开，统一在 CLI/MCP 前端。watch 的 pipeline 模式用于历史视频评价；实时 camera_observe 不强制执行完整视频评价。示范和实时图像都保留实际像素，并使用不同标记；来源哈希/stream ID 用于区分引用。

## 对当前分层方案的判断

CV/YOLO → Flash low → 执行模型是本项目的设计选择，不是 GPT-Policy 已经验证的等价复现。它可以降低主模型反复整理视频的负担，但也增加延迟和二次解释错误。实际帧必须可回看，阶段解释和不确定性不能替代原图。

目前 Flash 的三帧窗口适合快速预览，不保证保留所有接触细节。对完整示范应使用 prepare/compile 的阶段覆盖，缺证据时用 watch direct 重看时间点/区间。YOLO11n 的固定类别没有抽屉边缘/把柄；这层只能提供区域提议，不能充当抓取定位真值。

我们这次抓碗的文字指令已指定“抓把柄”。主要失败来自接近距离估计，这种问题不能只靠重复看示范解决。视频的新增价值需要同任务实验验证，不能由接口跑通或一次抓取成功推断。

建议最小对照：相同模型、相同设备/速度/初始场景与预算下，比“无示范”“只给摘要”“给实际关键帧”“关键帧+摘要”。分别记录成功、人工提示、动作数、时间与错误类型。先做少量试验检查协议，再扩大样本；不把三个试验的比例当作稳定成功率。
